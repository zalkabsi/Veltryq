# 2. Product Vision

## The problem

Traditional code review, static analysis, and unit tests frequently fail to catch certain business-logic defects.

A payment application may:

- Pass all conventional unit tests.
- Contain no obvious syntax errors.
- Pass standard vulnerability scanning.
- Compile and deploy successfully.

Yet it may still lose money because a financial invariant is violated.

Examples include:

- Processing the same refund twice.
- Crediting an account without the required debit.
- Allowing cumulative refunds to exceed captured payments.
- Applying incorrect currency rounding.
- Mishandling concurrent balance changes.
- Processing the same transaction more than once after a network timeout.

These errors can be difficult to detect because individual functions may appear correct while the overall financial workflow is inconsistent.

## The solution

Veltryq is an intelligent GitLab financial-integrity guardian.

When a developer submits code that affects financially sensitive operations, Veltryq should:

1. Detect the relevant change.
2. Understand which financial operations it affects.
3. Identify applicable business invariants.
4. Analyze possible failure scenarios.
5. Generate reproducible regression tests.
6. Execute the tests.
7. Capture proof of any discovered violation.
8. Propose a repair.
9. Validate the proposed repair.
10. Run additional security and quality checks.
11. Produce a structured evidence report.
12. Present a reviewed merge request and staging result.

The important distinction is that the AI should generate hypotheses and remediation proposals, while deterministic execution independently establishes whether the specified properties hold.

The project must never describe a property as mathematically proven when it has only been tested against a finite set of examples.

# 3. Product Differentiation

Do not build another generic AI code reviewer.

Veltryq must introduce three genuinely useful capabilities.

## A. Financial Invariant Verification

Create a reusable system of financial properties that can be checked automatically.

Initial supported invariants:

**Invariant 1 — Idempotency**

A repeated request with the same idempotency key must not produce a second successful financial posting.

**Invariant 2 — Ledger Balance**

For a defined double-entry transaction in one currency, total debits must equal total credits.

**Invariant 3 — Refund Limit**

The total successfully refunded amount for a captured payment cannot exceed its refundable balance.

**Invariant 4 — Monetary Precision**

Money must use an exact representation appropriate to its currency, such as integer minor units or a validated decimal representation.

**Invariant 5 — Transaction Atomicity**

A financial operation must not report a committed success if its required accounting state was only partially persisted.

Start with the first three invariants. Implement the remaining two only after the primary demonstration is working.

Do not assume these properties can be checked universally against arbitrary source code.

Implement explicit domain adapters, known execution paths, and well-defined test contracts.

## B. Counterexample Generation

When Veltryq suspects a financial defect, it must attempt to produce a concrete counterexample.

Example:

Original payment: $100

Requested refund: $100

First request: successful

Concurrent retry: unexpectedly successful

Total refund postings: $200

Expected maximum: $100

Invariant violated: idempotency and refund limit.

The system should create a test that reliably reproduces this behavior and records the resulting ledger entries.

Do not rely on screenshots of invented results.

## C. Evidence-Driven Repair

A generated patch alone is not sufficient.

Veltryq must produce:

- The vulnerable code reference.
- The relevant financial invariant.
- A reproducible failing test.
- The observed financial discrepancy.
- The proposed fix.
- A successful regression test after the fix.
- Relevant GitLab pipeline links.
- The test environment and limitations.
- A final review verdict.

This evidence is the main product differentiator.

# 4. Choose the Correct Implementation Scope

Because the competition deadline is close, optimize for a complete, verifiable end-to-end workflow.

The priority is one extraordinary working demonstration rather than ten incomplete capabilities.

## Required vertical slice

Build a realistic synthetic refund-processing application with a deliberately seeded concurrency/idempotency defect.

The application's normal tests should pass before Veltryq adds more targeted tests.

Veltryq must independently identify and reproduce the seeded defect.

Then it must create or propose a fix, rerun tests, and produce the final evidence.

The vulnerability should be realistic enough to teach something about transaction processing.

Avoid trivial examples such as `if amount > 100` being plainly reversed.

Prefer a defect involving a non-atomic check-and-write sequence, missing database uniqueness, or incorrect retry handling.

The failure must be reproducible in CI rather than dependent on luck or unstable timing.

## Chosen architecture

Use:

**Backend:** Python 3.12 with FastAPI.

**Persistence:** PostgreSQL, with transaction and uniqueness constraints.

**ORM:** SQLAlchemy.

**Migrations:** Alembic if required.

**Testing:** pytest and Hypothesis where valuable.

**Static checks:** Ruff, type checking if feasible, Bandit, and relevant dependency checks.

**CI/CD:** GitLab CI/CD.

**AI orchestration:** GitLab Duo Agent Platform, using a documented custom agent or custom flow.

**Report:** Self-contained HTML evidence report with a structured JSON equivalent.

**Optional deployment:** A minimal staging environment, preferably Google Cloud only if it can be deployed reliably without compromising the core project.

Avoid unnecessary microservices, Kubernetes, vector databases, complicated authentication frameworks, and large frontend dependencies.

Choose implementation simplicity where it improves reproducibility.

# 6. Build the Synthetic Financial Application

Implement a minimal but realistic payment-and-refund service.

The application must support:

- Creating a payment.
- Capturing a payment.
- Requesting a refund.
- Using an idempotency key.
- Recording double-entry ledger postings.
- Viewing synthetic transaction history.
- Retrieving refund state.

The backend must enforce explicit transaction states and monetary validation.

Use synthetic merchants and transactions only.

Do not connect to real payment processors or move real funds.

## Seeded defect

Introduce one controlled vulnerable version of the refund implementation.

Example mechanism:

1. The handler checks whether a refund exists.
2. It finds no existing refund.
3. Two requests pass the same initial check.
4. Both create refund postings before a database constraint prevents the duplicate.
5. The resulting state violates the expected financial invariant.

Ensure the actual defect mechanism is valid for the chosen database transaction isolation and schema.

If the proposed defect would be prevented by PostgreSQL constraints or normal database serialization, adjust the fixture until the vulnerability is real and reproducible.

A deterministic concurrency barrier may be used inside the test fixture.

The vulnerable code must be clearly identified as an intentionally insecure teaching example.

It must never be enabled in production.

# 7. Implement the Financial Invariant Engine

Create a domain-focused invariant evaluation framework.

An invariant must define:

- Unique identifier.
- Name.
- Description.
- Applicable financial operation.
- Required data.
- Preconditions.
- Test or evaluation strategy.
- Expected behavior.
- Failure evidence.
- Severity.
- Remediation guidance.

Keep this structure serializable.

Make checks deterministic when given the same input state.

## Invariant detection

Initially use an explicit mapping between sensitive application operations and applicable invariants.

For example:

- A refund-handler change activates refund-limit and idempotency tests.
- A ledger-posting change activates ledger-balance checks.
- A currency conversion change activates precision checks.

Optionally use an LLM to suggest additional invariants, but never trust an LLM-generated invariant without validation.

Record whether a candidate check is built-in, generated, or manually configured.

## Confidence representation

Differentiate:

- Confirmed violation: reproducible failure.
- Suspected violation: reasoning without reproduced evidence.
- Passed checks: selected tests passed.
- Inconclusive: unavailable data, unsupported operation, flaky environment, or insufficient coverage.

Never turn an unverified suspicion into a confirmed defect.

Never describe a limited test suite as proof that all financial bugs are absent.

# 8. Implement the Autonomous GitLab Workflow

This is one of the most important parts of the project.

The automation must genuinely run through the GitLab Duo Agent Platform.

A standard Python script launched by GitLab CI is useful but, by itself, is not sufficient to satisfy the requirement for real Duo agentic automation.

Create a custom agent or flow that participates meaningfully in the investigation, verification, and remediation process.

## Workflow trigger

Preferred trigger:

A merge request changes a financially sensitive file.

Alternative:

A developer starts the Veltryq custom flow on an existing merge request.

Select whichever trigger is actually supported and can be demonstrated reliably.

Do not invent an event trigger.

## Stage 1 — Analyze

Read the merge-request diff and relevant source context.

Determine whether the change touches:

- Refund processing.
- Payment settlement.
- Ledger posting.
- Balance adjustments.
- Transaction retries.
- Currency precision.

Retrieve GitLab data through documented, authenticated APIs or agent tools.

Produce a concise impact assessment.

## Stage 2 — Investigate

The agent identifies potentially violated business invariants and selects appropriate checks.

Generate concrete test scenarios.

For the primary demo, include concurrent duplicate refund requests.

Run these scenarios against the vulnerable application.

Collect exact test output and database-state evidence.

## Stage 3 — Remediate

The agent proposes a repair.

The repair should use an appropriate mechanism such as:

- Database uniqueness constraints.
- Transactional conflict handling.
- Atomic state updates.
- Correct transaction boundaries.
- Safe idempotency replay semantics.

Do not introduce arbitrary sleeps, global process locks, or other superficial techniques that fail in multi-process deployments.

The fix must preserve the expected behavior for legitimate requests.

Prefer a separate remediation branch and merge request, or an explicit patch proposal if the available Duo tools cannot safely create branches.

## Stage 4 — Verify

Run the previously failing regression test against the repair.

Run existing unit tests, integration tests, and financial invariants.

Check that the repair does not break partial refunds or other valid scenarios.

Produce before-and-after evidence.

## Stage 5 — Secure

Run appropriate security checks.

At minimum:

- Dependency vulnerability review.
- Secret detection.
- Static security analysis.
- Input-validation tests.
- Authentication and authorization review of any management endpoints.
- Checks against unsafe tool execution.

Use native GitLab security scanning features where available and documented.

Do not falsely claim GitLab Ultimate security features are enabled when they are not.

## Stage 6 — Review

Publish a structured GitLab merge-request comment containing:

- Risk level.
- Financial invariant.
- Affected files.
- Confirmed failure.
- Reproduction instructions.
- Proposed remediation.
- Verification results.
- Pipeline status.
- Evidence artifact links.
- Reviewer actions required.

## Stage 7 — Stage the Fix

If time and deployment permissions allow, deploy the repaired application to an isolated staging environment after the appropriate CI checks pass.

Run a smoke test against staging.

Production release must require explicit authorization.

Do not use real financial data.

## Stage 8 — Observe

Capture meaningful execution information, including:

- Agent/flow execution status.
- Analysis duration.
- Invariant checks executed.
- Confirmed failures.
- Remediation attempts.
- CI job results.
- Staging smoke-test status.

Use GitLab pipeline artifacts and logs first.

Integrate OpenTelemetry only if the core workflow is already reliable.

## Stage 9 — Govern

Produce a final audit record connecting:

- Original merge request.
- Source commit SHA.
- Evidence and failing tests.
- Proposed remediation commit.
- Verification pipeline.
- Reviewer decision.
- Final outcome.

Every meaningful conclusion must link to evidence.

The agent may perform analysis, generate tests, and prepare fixes autonomously.

Human approval is required before merging or promoting financial-system changes to production.

# 12. Testing Strategy

Testing quality is more important than the number of tests.

## Functional tests

Verify that:

- Payments can be created.
- Payments can be captured.
- Valid refunds succeed.
- Repeated idempotency keys return a consistent prior result without duplicate postings.
- Refund limits are enforced.
- Ledger transactions remain balanced.

## Concurrency tests

Verify simultaneous refund requests.

Use deliberate synchronization to reproduce the seeded race condition deterministically.

Run the test repeatedly to establish reliability.

## Regression tests

The exact scenario that fails against vulnerable code must pass against the repair.

Do not modify the test merely to make the patch appear successful.

## Negative tests

Include:

- Negative amounts.
- Zero amounts.
- Excessive refund amounts.
- Unknown payment IDs.
- Duplicate idempotency keys with conflicting payloads.
- Unsupported currencies.
- Invalid state transitions.
- Simulated failures during transaction processing.

## Agent evaluation

Test the agent against a small synthetic benchmark:

- Duplicate refund: vulnerable.
- Normal refund: safe.
- Ledger imbalance: vulnerable.
- Unrelated documentation change: safe.

Measure:

- Confirmed defect detection.
- False positive behavior.
- Correct test reproduction.
- Repair success.
- Pipeline completion.
- Execution duration.

If any case is not implemented, exclude it from reported metrics rather than pretending it was evaluated.

Use only measured values.
